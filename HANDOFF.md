## 1. What this is

A site where a buyer picks a Bible verse, personalizes a certificate of dedication (recipient name,
their own name or anonymous, optional short message), pays, and receives a personalized PDF
certificate. Two tiers. 10% of every purchase is given to **Pioneer Bible Translators**
(EIN 23-7433923).

## 2. Feature status

### Implemented and verified

- Browse + filter verses by theme; search by reference, text, or theme name.
- Verse cards show a public dedication count (`verse_dedication_counts` view).
- Public dedication feed, opt-in per order.
- Personalize modal with a **live certificate preview**, recipient/name/message, 140-char counter.
- Stripe Checkout, created server-side. Browser sends only a tier key; price resolves on the server.
- **Idempotent** Stripe webhook: records the order, creates the dedication with a race-safe per-verse
  number, generates the PDF, uploads to Supabase Storage, emails the link.
- Certificate PDF: 792×612pt landscape, painted template + vector text, embedded OFL fonts.
- **Verse requests** — a visitor can request a verse we don't carry. Stored in `verse_requests`,
  optional confirmation email to them, notification to the owner. UI promises **within 24 hours**.
- **Loud failure on outages** — see §5, this one matters.
- Branded OG/Twitter share card (`public/og-image.png`, generated by `assets/make_og_image.py`).
- SEO: metadata, JSON-LD, `sitemap.xml`, `robots.txt`, favicon.
- A11y: `role="dialog"`/`aria-modal`/Escape/scroll-lock, `aria-expanded` FAQ, `aria-pressed` filters.
- Admin `/admin` (shared-password) for order fulfilment.

### Not built

- `/order/[id]` — buyer-facing re-download of a certificate.
- Admin UI for `verse_requests` (query the table directly for now; SQL is in the README).
- Admin takedown for public dedications.
- Rate limiting on `/api/create-checkout-session`. `/api/verse-request` has an in-memory throttle
  only, which is a speed bump, not real defence (§6).
- Certificate regeneration job for "paid but PDF failed".

## 4. Data model

Schema source of truth: `db/schema.sql` + `db/seed.sql`. **`db/setup.sql` is generated** — do not edit
it. Regenerate with `bash scripts/make-setup-sql.sh`.

Tables: `themes`, `verses`, `verse_themes`, `orders`, `dedications`, `verse_requests`.
View: `verse_dedication_counts` (`security_invoker = true`, counts public dedications only).

Three things in the schema are load-bearing and non-obvious:

1. **`unique (verse_id, dedication_number)`** plus the `set_dedication_number()` trigger. The trigger
   does `max+1`, which races under concurrency; the constraint catches it and the app retries on
   Postgres `23505`. Do not remove the constraint.
2. **`count(*)::int`** in the view. PostgREST returns `bigint` as a *string*, so without the cast the
   client receives `"3"` and any arithmetic silently does string concatenation.
3. **`security_invoker = true`** on the view. Without it the view runs as its owner and bypasses RLS,
   which would expose private dedications' counts.

### RLS

Enabled on all five original tables plus `verse_requests`.

- `verses`, `themes`, `verse_themes` — public SELECT.
- `dedications` — SELECT only where `is_public = true`.
- `orders` — **no policy.** Service-role only.
- `verse_requests` — **no policy, deliberately.** It stores requester names and email addresses.
  Adding a SELECT policy for `anon` would leak every requester's email. It is written and read only
  by the server through the service role. If someone later adds a public read here, that is a bug.

## 5. The most important thing in this codebase

**A database outage used to look exactly like "no data yet".**

`src/lib/verseData.js` previously did:

```js
const { data } = await supabasePublic.from('themes').select(...)
return data || []          // ← error discarded
```

`error` was thrown away entirely. So when Supabase was unreachable, the site did not break — it
rendered a cheerful *"No verses in this theme yet"*, and every verse page 404'd (because
`fallback: 'blocking'` with "no verse found" means `notFound: true`). A dead database and an empty
database were visually identical. This genuinely hid a multi-hour outage.

Every read now goes through `unwrap()`, which throws `DataUnavailableError`. Consequences:

- `getStaticProps` on `/` returns `dataUnavailable: true`, and the UI says the library is
  *temporarily unavailable* and still offers the request flow.
- `/verse/[slug]` fails loudly.
- **`fetchVerseSlugs()` deliberately still does NOT throw.** It runs during `next build`, and a blip
  must not fail a build. Both callers recover: `fallback: 'blocking'` regenerates verse pages on
  first request, and the sitemap is regenerated hourly.
- Dedication counts are decorative — a failure there degrades to zero counts rather than blanking
  the grid.

**Keep this behaviour.** If you refactor these helpers, preserve "outage is loud, build never fails".

## 6. Verse requests — how it works

`POST /api/verse-request` with `{ reference, requester_name, requester_email, note }`.

Validation: reference 2–120 chars and **not more than 14 words** (stops a pasted paragraph being
filed as a "reference"); email optional but format-checked if present; name ≤80, note ≤400. The DB
enforces the same length limits as a backstop.

On success the row is inserted with `status = 'pending'`, then **two best-effort emails** are sent:
a confirmation to the requester (only if they gave an email) and a heads-up to `CONTACT_EMAIL`.
Email failure never fails the request — the row is already saved, and the visitor still sees the
confirmation.

The **24-hour promise** appears in three places: the UI copy, `VERSE_REQUEST_ETA` in
`src/lib/email.js`, and the API's `eta` field. If you change the SLA, change all three or they drift.

**Throttle caveat:** `throttled()` is an in-memory `Map`. Serverless instances are ephemeral and
there may be several, so this only catches accidental double-submits. If verse requests are ever
abused, replace it with a real store — a D1/KV counter or an Upstash rate limit.

## 7. Deployment

Full sequence in `docs/DEPLOYMENT.md`. The short version:

1. **Supabase** → SQL Editor → run `db/setup.sql` (safe to re-run; verified). Then create a Storage
   bucket named `certificates`, public.
2. **Vercel** → Project → Import Git Repository → `campsab1230/Versededication.com`. Next.js
   auto-detects.
3. **Environment variables** (Production *and* Preview) — see §8. Set them **before** the first
   deploy, or the build bakes in nothing and you get an empty site.
4. **Stripe** → Developers → Webhooks → add `https://versededication.com/api/stripe-webhook`,
   event `checkout.session.completed`. Copy the `whsec_…`.
5. **Domains** → add `versededication.com` and `www.versededication.com`, create the DNS records
   Vercel shows (`A @ 76.76.21.21`, `CNAME www cname.vercel-dns.com` — use whatever Vercel renders),
   then set apex canonical and `www` → 301 → apex.

### ⚠️ Ordering trap

`NEXT_PUBLIC_SITE_URL` and the Stripe webhook URL must both match the **canonical** hostname. Set
canonical → update both → redeploy. Get it backwards and checkout redirects, canonical tags, and
emailed certificate links all point at the wrong host.

**`versededication.com` currently has no DNS records at all** — it resolves to nothing. That is the
one remaining gap between this repo and a live site on that domain.

### ⚠️ Do not build on Windows

The toolchain ships native binaries that break the serverless bundle. Build on Linux/macOS/CI.
Vercel builds in the cloud, so this only matters for self-hosting.

## 10. Known issues and gotchas

| Symptom | Cause / fix |
|---|---|
| Empty verse grid, every `/verse/*` 404s | Database unreachable. Check the server logs — since the §5 fix it logs `Supabase read failed (…): fetch failed`. Previously this was silent. |
| `sitemap.xml` shows a `*.vercel.app` host | `NEXT_PUBLIC_SITE_URL` unset in Vercel; `siteUrl()` fell back to `VERCEL_URL` |
| Webhook 400s | `STRIPE_WEBHOOK_SECRET` doesn't match the endpoint, or the raw-body config was removed |
| No certificate URL | Bucket missing, or service-role key unset/rotated |
| No email | `RESEND_API_KEY` / `EMAIL_FROM` unset, or sending domain unverified |
| Duplicate dedication numbers | The unique constraint from `db/schema.sql` wasn't applied |
| `next dev` returns 500 on every API route | Running dev over a `.next` containing **production** output. Fix: `rm -rf .next` then `npm run dev`. This bit me during this session. |
| `create-checkout-session` → `400 "A verse must be selected."` | `verse_id` is a **UUID**, not a slug, and must be a **string**. Look it up: `select id from verses where slug = 'psalm-23-1-4'` → `15fecc55-…`. Sending `1` or a slug fails validation *before* Stripe is ever called, so a 400 here says nothing about `STRIPE_SECRET_KEY`. |
| Locked env var that "can't be edited" | It's owned by a **Vercel integration** (the blue `S` badge = Stripe). The integration reads and syncs the value, so the field is read-only by design — not a misconfiguration, and not something you need to change. |
| Checkout URL is `cs_test_…` | Keys are **test mode**. Fine for launch rehearsal; swap in live keys before taking real money. |

### Supabase projects can vanish from DNS

The Supabase project was unreachable for part of this session: `oesdrtslwqaycqyxqbqj.supabase.co`
returned **NXDOMAIN** on authoritative DNS, then came back when the project was restored. Note that a
*paused* project drops its DNS record too — so **NXDOMAIN alone does not prove deletion.** Free-tier
projects pause after ~7 days idle and are deleted after ~90 days; a live consumer site should not sit
on a free project without a keep-alive.

## 11. Local development

```bash
npm install
cp .env.example .env.local     # then fill it in
rm -rf .next                   # if you previously ran a production build
npm run dev                    # http://localhost:3000
```

Stripe webhooks locally:

```bash
stripe listen --forward-to localhost:3000/api/stripe-webhook
stripe trigger checkout.session.completed
```

A bare `trigger` carries no dedication metadata, so the handler will reject it — that is expected.
The real test is a full checkout through the site with card `4242 4242 4242 4242`.

Useful scripts:

```bash
node scripts/render-sample.mjs     # render certificate PDFs from fixtures (no DB needed)
bash scripts/make-setup-sql.sh     # regenerate db/setup.sql
```

`scripts/render-sample.mjs` includes a `noNames` regression case asserting that a certificate with no
recipient and no dedicator draws **no substitute name**. Keep it: an earlier version invented
`'A Beloved Friend'` and `'Scripture'` fallbacks, which printed fabricated text on a real customer's
certificate.
