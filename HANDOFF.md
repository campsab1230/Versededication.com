## 4. Data model

Schema source of truth: `db/schema.sql` + `db/seed.sql`. **`db/setup.sql` is generated** — do not edit
it. Regenerate with `bash scripts/make-setup-sql.sh`.

Tables: `themes`, `verses`, `verse_themes`, `orders`, `dedications`, `verse_requests`.
View: `verse_dedication_counts` (`security_invoker = true`, counts public dedications only).

Three things in the schema are load-bearing and non-obvious:

1. **`unique (verse_id, dedication_number)`** plus the `set_dedication_number()` trigger. The trigger
   does `max+1`, which races under concurrency; the constraint catches it and the app retries on
   Postgres `23505`. Do not remove the constraint.
2. **`count(*)::int`** in the view. PostgREST returns `bigint` as a *string*, so without the cast the
   client receives `"3"` and any arithmetic silently does string concatenation.
3. **`security_invoker = true`** on the view. Without it the view runs as its owner and bypasses RLS,
   which would expose private dedications' counts.

### RLS

Enabled on all five original tables plus `verse_requests`.

- `verses`, `themes`, `verse_themes` — public SELECT.
- `dedications` — SELECT only where `is_public = true`.
- `orders` — **no policy.** Service-role only.
- `verse_requests` — **no policy, deliberately.** It stores requester names and email addresses.
  Adding a SELECT policy for `anon` would leak every requester's email. It is written and read only
  by the server through the service role. If someone later adds a public read here, that is a bug.

## 5. The most important thing in this codebase

**A database outage used to look exactly like "no data yet".**

`src/lib/verseData.js` previously did:

```js
const { data } = await supabasePublic.from('themes').select(...)
return data || []          // ← error discarded
```

`error` was thrown away entirely. So when Supabase was unreachable, the site did not break — it
rendered a cheerful *"No verses in this theme yet"*, and every verse page 404'd (because
`fallback: 'blocking'` with "no verse found" means `notFound: true`). A dead database and an empty
database were visually identical. This genuinely hid a multi-hour outage.

Every read now goes through `unwrap()`, which throws `DataUnavailableError`. Consequences:

- `getStaticProps` on `/` returns `dataUnavailable: true`, and the UI says the library is
  *temporarily unavailable* and still offers the request flow.
- `/verse/[slug]` fails loudly.
- **`fetchVerseSlugs()` deliberately still does NOT throw.** It runs during `next build`, and a blip
  must not fail a build. Both callers recover: `fallback: 'blocking'` regenerates verse pages on
  first request, and the sitemap is regenerated hourly.
- Dedication counts are decorative — a failure there degrades to zero counts rather than blanking
  the grid.

**Keep this behaviour.** If you refactor these helpers, preserve "outage is loud, build never fails".

## 6. Verse requests — how it works

`POST /api/verse-request` with `{ reference, requester_name, requester_email, note }`.

Validation: reference 2–120 chars and **not more than 14 words** (stops a pasted paragraph being
filed as a "reference"); email optional but format-checked if present; name ≤80, note ≤400. The DB
enforces the same length limits as a backstop.

On success the row is inserted with `status = 'pending'`, then **two best-effort emails** are sent:
a confirmation to the requester (only if they gave an email) and a heads-up to `CONTACT_EMAIL`.
Email failure never fails the request — the row is already saved, and the visitor still sees the
confirmation.

The **24-hour promise** appears in three places: the UI copy, `VERSE_REQUEST_ETA` in
`src/lib/email.js`, and the API's `eta` field. If you change the SLA, change all three or they drift.

**Throttle caveat:** `throttled()` is an in-memory `Map`. Serverless instances are ephemeral and
there may be several, so this only catches accidental double-submits. If verse requests are ever
abused, replace it with a real store — a D1/KV counter or an Upstash rate limit.

## 7. Deployment

Full sequence in `docs/DEPLOYMENT.md`. The short version:

1. **Supabase** → SQL Editor → run `db/setup.sql` (safe to re-run; verified). Then create a Storage
   bucket named `certificates`, public.
2. **Vercel** → Project → Import Git Repository → `campsab1230/Versededication.com`. Next.js
   auto-detects.
3. **Environment variables** (Production *and* Preview) — see §8. Set them **before** the first
   deploy, or the build bakes in nothing and you get an empty site.
4. **Stripe** → Developers → Webhooks → add `https://versededication.com/api/stripe-webhook`,
   events `checkout.session.completed` **and** `checkout.session.async_payment_succeeded`.
   Copy the `whsec_…`. See §18 — subscribing to only the first event can silently lose a paid order.
5. **Domains** → add `versededication.com` and `www.versededication.com`, create the DNS records
   Vercel shows (`A @ 76.76.21.21`, `CNAME www cname.vercel-dns.com` — use whatever Vercel renders),
   then set apex canonical and `www` → 301 → apex.

### ⚠️ Ordering trap

`NEXT_PUBLIC_SITE_URL` and the Stripe webhook URL must both match the **canonical** hostname. Set
canonical → update both → redeploy. Get it backwards and checkout redirects, canonical tags, and
emailed certificate links all point at the wrong host.

**`versededication.com` currently has no DNS records at all** — it resolves to nothing. That is the
one remaining gap between this repo and a live site on that domain.

### ⚠️ Do not build on Windows

The toolchain ships native binaries that break the serverless bundle. Build on Linux/macOS/CI.
Vercel builds in the cloud, so this only matters for self-hosting.

## 10. Known issues and gotchas

| Symptom | Cause / fix |
|---|---|
| Empty verse grid, every `/verse/*` 404s | Database unreachable. Check the server logs — since the §5 fix it logs `Supabase read failed (…): fetch failed`. Previously this was silent. |
| `sitemap.xml` shows a `*.vercel.app` host | `NEXT_PUBLIC_SITE_URL` unset in Vercel; `siteUrl()` fell back to `VERCEL_URL` |
| Webhook 400s | `STRIPE_WEBHOOK_SECRET` doesn't match the endpoint, or the raw-body config was removed |
| No certificate URL | Bucket missing, or service-role key unset/rotated |
| No email | `RESEND_API_KEY` / `EMAIL_FROM` unset, or sending domain unverified |
| Duplicate dedication numbers | The unique constraint from `db/schema.sql` wasn't applied |
| `next dev` returns 500 on every API route | Running dev over a `.next` containing **production** output. Fix: `rm -rf .next` then `npm run dev`. This bit me during this session. |
| `create-checkout-session` → `400 "A verse must be selected."` | `verse_id` is a **UUID**, not a slug, and must be a **string**. Look it up: `select id from verses where slug = 'psalm-23-1-4'` → `15fecc55-…`. Sending `1` or a slug fails validation *before* Stripe is ever called, so a 400 here says nothing about `STRIPE_SECRET_KEY`. |
| Locked env var that "can't be edited" | It's owned by a **Vercel integration** (the blue `S` badge = Stripe). The integration reads and syncs the value, so the field is read-only by design — not a misconfiguration, and not something you need to change. |
| Checkout URL is `cs_test_…` | Keys are **test mode**. Fine for launch rehearsal; swap in live keys before taking real money. |

### Supabase projects can vanish from DNS

The Supabase project was unreachable for part of this session: `oesdrtslwqaycqyxqbqj.supabase.co`
returned **NXDOMAIN** on authoritative DNS, then came back when the project was restored. Note that a
*paused* project drops its DNS record too — so **NXDOMAIN alone does not prove deletion.** Free-tier

on a free project without a keep-alive.

## 14. Pointing versededication.com at Vercel

The domain's nameservers are **Cloudflare** (`apollo.ns.cloudflare.com`, `veronica.ns.cloudflare.com`),
so all records below are added in the **Cloudflare dashboard**, not at the registrar.

### Working configuration (verified live)

| Type | Name | Value | Proxy |
|---|---|---|---|
| `CNAME` | `@` | `cc935033ed9ba5b5.vercel-dns-017.com` | **Proxied** (orange) |
| `CNAME` | `www` | `cc935033ed9ba5b5.vercel-dns-017.com` | **Proxied** (orange) |

This is what is actually deployed and verified: **CNAME at the apex**, Cloudflare-flattened, with the
orange proxy **on**. Cloudflare terminates TLS at the edge (Let's Encrypt, `CN=versededication.com`) and
passes through to Vercel — responses carry `x-vercel-cache` and `x-vercel-id`.

Do **not** pre-emptively switch the proxy off. It works, and it is the configuration to keep.

### Order

1. Vercel → project → **Settings → Domains** → add `versededication.com` *and* `www.versededication.com`.
2. Copy the **CNAME target** from the domain card.
3. Cloudflare → **DNS → Records** → add both rows above.
4. The apex 308-redirects to `https://www.versededication.com/` once `www` is the primary domain.

### Alternative: the A-record recipe

Most guides (and Vercel's own KB) describe `A @ → 76.76.21.21` plus a `www` CNAME, proxy off. That also
works — it is simply **not** what was done here, so do not "correct" the working zone to match it. If you
do use it, the domain card's IP is the source of truth, not the IP printed in any guide.

### Gotchas that actually bite

- **No AAAA records** on the apex. Vercel does not support IPv6 for third-party-DNS custom domains, and
  an AAAA splits traffic so the certificate challenge lands elsewhere.
- **Flexible SSL** causes `err_too_many_redirects`. Use **Full**.
- A `CAA` record that omits Let's Encrypt blocks issuance.
- Stuck on "Invalid Configuration" with apparently-correct records? Remove the domain from the project
  and re-add it to reset the check. If the proxy is on, toggle that record to DNS-only while Vercel
  re-verifies, then turn it back on.

## 15. Resend (outbound email)

Both `sendCertificateEmail` and `sendVerseRequestEmail` send through Resend, and both return
`{ skipped: true }` / `{ ok: false }` rather than throwing, so **a broken mail config fails silently** —
orders and verse requests are still recorded, but no email arrives.

As of 2026-10-19 the live `POST /api/verse-request` returns `emailed: false`, so mail is **not** going
out yet. `RESEND_API_KEY` exists in Vercel, so the likely blocker is that the sending domain is not
verified — `EMAIL_FROM` is `certificates@versededication.com`.

### Fix

1. Resend → **Domains** → **Add Domain** → `versededication.com`.
2. Either click **Sign in to Cloudflare** (Domain Connect adds the records automatically), or add them
   by hand in Cloudflare → **DNS → Records**:

   | Type | Name | Content | Priority | Proxy |
   |---|---|---|---|---|
   | `MX` | `send` | `feedback-smtp.<region>.amazonses.com` | `10` | DNS only |
   | `TXT` | `send` | `v=spf1 include:amazonses.com ~all` | — | DNS only |
   | `TXT` | `resend._domainkey` | `p=…` (long DKIM key) | — | DNS only |

   **Copy the exact values from Resend.** The region in the MX host varies per account.
3. **Every one of these must be DNS only (grey cloud).** A proxied record makes Resend's check fail;
   Cloudflare returns error `1004` for a proxied CNAME.
4. Resend → **Verify DNS Records**. Often minutes, officially up to 72h.
5. Optional: toggle **Receiving** on if mail to the domain should be accepted (adds an `inbound` MX).

### Then check

```bash
curl -s -X POST https://www.versededication.com/api/verse-request \
  -H 'Content-Type: application/json' \
  -d '{"reference":"Test 1:1","requester_name":"Me","requester_email":"you@example.com"}'
# want emailed:true
```

If it still says `false`, the value is in the Vercel function log for that invocation.

### Why `emailed:false` was undiagnosable — now FIXED

`sendVerseRequestEmail` returns `ok:false` for several different causes (no API key, unverified sending
domain, bad key, network). The endpoint reported all of them as a bare `emailed:false`, so a silent mail
outage looked identical to "Resend is not configured".

`src/pages/api/verse-request.js` now also returns **`emailReason`** (null when the mail was sent):

| value | meaning |
|---|---|
| `not_configured` | `RESEND_API_KEY` is empty in the Vercel environment |
| `domain_not_verified` | Resend returned **403** — the sending domain is not verified yet. This is the usual cause right after adding a domain. |
| `resend_http_<code>` | Resend rejected the send with that status |
| `no_recipient` | no requester email and no admin address to notify |
| `network_error` | the fetch to Resend threw |
| `threw` | an unexpected exception in the endpoint |

A failure also writes `[verse-request] email not sent: <reason>` to the Vercel function log.

**Check it with:**

```bash

  -H 'Content-Type: application/json' \
```

### Trap: duplicate DKIM records at one selector (found 2026-10-19)

`resend._domainkey.versededication.com` has **two** TXT records (both 218 chars). DKIM requires exactly
one key per selector. Two happens when the domain is added in a *second* Resend account without the
first account's records being removed — the new account adds its key alongside the stale one.

Effect: DKIM verification becomes undefined/intermittent (some verifiers concatenate the strings), so
mail can fail authentication and land in spam. It does **not** cause a 401 — that is always the API key.

| Record | Prefix after `p=` | Origin |
|---|---|---|
| stale | `MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQCXrcxmSuayy7lu...` | prior Resend account |
| current | `MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC+5wnzl5yj+VQS8pRf...` | account signed into on 2026-10-19 |

Delete the stale one; keep the value the live Resend dashboard shows. To check:


### `resend_http_401` = the key, not the domain

Signing into Resend and verifying the domain does **not** change the key already stored in Vercel.
A 401 from Resend means the key is invalid/revoked/orphaned — typically because Vercel still holds the
key from a **previous** Resend account. `403` is the domain-not-verified case; `401` is never that.

Fix: resend.com (the account in use now) → API Keys → create → update `RESEND_API_KEY` in Vercel →
**redeploy**. Env vars are injected at deploy time, so editing the variable alone changes nothing.

### RESOLVED 2026-10-19: email sends; delete the OLD DKIM key

`POST /api/verse-request` now returns `{"emailed":true,"emailReason":null}`. The 401 was cleared by
replacing `RESEND_API_KEY` with a key from the Resend account signed into on 2026-10-19.

**Which duplicate DKIM record to delete — evidence, not a guess.** Observed directly:

| When | Records at `resend._domainkey` |
|---|---|
| before the new Resend account verified | **one** — `...XrcxmSuayy...` |
| after it verified | **two** — `...+5wnzl5yj...` and `...XrcxmSuayy...` |

So `+5wnzl` was *added* by the new account; `Xrcxm` predates it and belongs to the previous account.
Consistency check: the API key now in use is the **new** account's, and it is the new account that signs
outgoing mail — so its key (`+5wnzl`) is authoritative.

**Keep** the value ending `...E9Z/pwIDAQAB` (`+5wnzl`). **Delete** the one ending `...VSAqGQ0wIDAQAB`

Both render identically in Cloudflare's list (`"p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADC...`) because the UI

## 16. Database security audit (2026-10-19)

An unauthenticated audit of the live Supabase project (`oesdrtslwqaycqyxqbqj`) found, and left,
**one item open**.

### The `dedications` column leak — STILL OPEN at time of writing

RLS filters **rows**, not **columns**. Supabase grants `anon` and `authenticated` a blanket
`GRANT SELECT ON ALL TABLES` on the public schema, so the existing

```sql
create policy "Public can read public dedications" on dedications
  for select using (is_public = true);
```

only decided *which* dedications are visible. Every column of a visible row stayed readable by
anyone holding the anon key — which ships in the browser bundle.

Reproduced with a canary row (inserted with the service role, then deleted). Re-run 2026-10-19 and
still reproducing:

| anon request | observed | expected once fixed |
|---|---|---|
| `?select=message` | `200 [{"message":"PROBE-2"}]` | `401 permission denied` |
| `?select=*` | `200` — full row incl. `order_id`, `certificate_url` | `401` |
| `?select=recipient_name,dedicator_name,…` (the feed query) | `200` | `200` — unchanged |
| `verse_dedication_counts` | `200` | `200` — unchanged |

`certificate_url` is the sharp edge: the `certificates` bucket is **public**, so that URL downloads
the personalised PDF with no auth at all. This directly contradicts `src/pages/privacy.js`, which
promises only first name / verse reference / recipient name are ever public.

**The fix is committed in this repo** (`db/schema.sql`, regenerated into `db/setup.sql`) — a
guarded, idempotent `do $$ … $$` block that revokes the blanket grant and re-grants exactly the
nine feed columns. **It is not live until it is run against the database.** See §17.

Validated in a scratch PostgreSQL 17.11 before shipping: leak reproduced pre-fix, blocked post-fix,
feed and count view unaffected, and the block is a clean no-op on a database with no `anon` role.

### What the audit cleared

| Check | Result |
|---|---|
| `orders` / `verse_requests` anon read | `200 []` — no policy, correctly unreadable |
| anon INSERT into `verses` | `401` `42501` RLS violation |
| anon DELETE / PATCH on `verses` | `204` **with no effect** |
| anon key in the client bundle | absent — 0 matches in shipped JS; every anon query is server-side in `getStaticProps` |

⚠️ **`204` on a DELETE is the trap in this table.** It reads like success and means the opposite:
*0 rows matched the RLS filter*. Proven with a canary row that survived the request.

## 18. Stripe webhook: fulfilment was not gated on payment

**Found and fixed 2026-10-19.** The original handler fulfilled on *every*
`checkout.session.completed`:

```js
case 'checkout.session.completed':
  await handleCheckoutCompleted(event.data.object);   // <- unconditional
```

That event does **not** mean the money arrived. For *delayed* payment methods (ACH / bank debits,
some wallets) Stripe fires `checkout.session.completed` while `payment_status` is still `unpaid`,
and only later fires `checkout.session.async_payment_succeeded` once the funds settle. Fulfilling
unconditionally would mint a dedication, generate and upload the certificate PDF, and email the
customer — for a payment that may never clear. The PDF costs nothing to produce, but the Heirloom
tier is a **physical item that would have shipped**.

### The fix

The handler now skips only when the session is explicitly unpaid, and treats the async event as a
second fulfilment trigger:

```js
if (event.data.object.payment_status === 'unpaid') { /* log, break */ }
await handleCheckoutCompleted(event.data.object);
// plus: case 'checkout.session.async_payment_succeeded': -> same handler
```

**`=== 'unpaid'`, not `!== 'paid'`.** This is the trap. Stripe's own
[fulfilment guide](https://docs.stripe.com/checkout/fulfillment) uses
`if checkout_session.payment_status != 'unpaid'`, because `no_payment_required` — a 100%-discounted
or zero-total session — is a *completed sale that must still be fulfilled*. An inverted check that
accepts only exactly `'paid'` silently strands those orders.

### I got that wrong first, and my own test agreed with me

The first patch used `!== 'paid'`. The guard test "passed" 5/5 — because I had written
`no_payment_required -> expect 0 fulfilled` into the expectations, encoding my own wrong assumption
as the pass condition. It was only caught by reading Stripe's docs, not by the test.

Lesson worth keeping: **a test whose expectations come from the same head that wrote the code proves
nothing.** Expectations must come from an external authority (the vendor's docs) or from observed
production behaviour. The reworked test reads expectations from the docs and now covers
`paid`, `unpaid`, `no_payment_required`, `async_payment_succeeded`, an unrelated event, and
`async_payment_failed`. All six pass.

The test runs the **real switch block extracted from the source file** (`/tmp/guard-test2.mjs`)
rather than a hand-copied re-implementation, so it cannot silently drift from what ships.

### ⚠️ New deployment dependency — the fix is only safe once this is done

Because the handler now *skips* unpaid sessions, the endpoint **must** be subscribed to
`checkout.session.async_payment_succeeded`, or a delayed-method order is charged and never fulfilled.
`docs/DEPLOYMENT.md` previously said to subscribe to `checkout.session.completed` only; that has been
corrected, and §7 step 4 links here.

**Action:** Stripe → Developers → Webhooks → your endpoint → confirm **both** events are selected.
`stripe listen --forward-to` forwards everything by default, so a successful local test does **not**
prove the deployed endpoint is subscribed to the async event.

This is live the moment a delayed payment method is enabled in the Dashboard, because
`create-checkout-session.js` does not pin `payment_method_types` — it inherits whatever dynamic
payment methods Stripe has enabled. Either subscribe to the event, or switch delayed methods off.

### Also fixed: `amount_total ||` recorded the wrong amount on a $0 session

```js
amount_cents: session.amount_total || tierConfig.amountCents,   // before
amount_cents: session.amount_total ?? tierConfig.amountCents,   // after
```

`0` is a legitimate `amount_total` (a $0 / `no_payment_required` session), but `0 || 1499`
evaluates to `1499`. A session that collected nothing was recorded as a full-price Heirloom order,
inflating revenue and mis-stating the order. `??` falls back only on `null`/`undefined`.

Proven by extracting the real expression from the shipped file and diffing old vs new:
799→799, 1499→1499, `0`→**0** (was 1499), `null`→1499. 4/4.

### ⚠️ Latent, NOT fixed: idempotency is skipped when `payment_intent` is null

The duplicate-delivery guard is:

```js
const paymentIntentId = session.payment_intent || null;
if (paymentIntentId) { /* look for an existing order */ }
```

Stripe's API reference lists `payment_intent` as **nullable** on a Checkout Session. When it is
null, the guard is skipped entirely, so a second delivery of the same event would create a
**second order and a second dedication**, with a new `dedication_number`, and email the customer
again.

Nothing below catches it:

- `orders.stripe_payment_intent_id` is `unique` — but the value is `NULL`, and Postgres permits
  unlimited NULLs in a unique column, so the constraint never fires.
- `dedications_verse_number_unique` is `(verse_id, dedication_number)` and the trigger hands the
  second insert a *fresh* number, so it does not fire either.

**Why this is latent rather than live:** the current checkout cannot produce such a session.
`allow_promotion_codes` is never set and both tiers price from `src/lib/pricing.js` (799 / 1499),
so a customer has no way to reach a $0 total. It becomes reachable if `STRIPE_PRICE_DIGITAL` /
`STRIPE_PRICE_HEIRLOOM` are ever set to a $0 Price, or promotion codes are switched on, or an
order is fully discounted in the Dashboard.

**Not verified:** whether Stripe actually leaves `payment_intent` null on a completed `$0` session.
I could not test this without live keys, so treat it as defensive, not confirmed.

**Recommended fix (needs a migration, so deliberately not shipped unannounced):** add
`stripe_session_id text unique` to `orders`, always populated from `session.id` (which is never
null), and make the guard check `payment_intent` **or** `stripe_session_id`.

⚠️ If that is done, **run the SQL before deploying the code** — new code querying a column that
does not exist yet would break the money path. The reverse order is safe.

### Still open from §16

The `dedications` column leak remains **unfixed on the live database** (verified again this session:
anon `?select=message` still returns `200` with data). The SQL is committed and ready in §16/§17.

## 19. Admin surface audit (2026-10-19)

There are exactly **four** API routes. Live status, unauthenticated:

| Route | GET without auth | Note |
|---|---|---|
| `/api/admin/orders` | **401** `Not signed in.` | gated on `ADMIN_SECRET` cookie |
| `/api/create-checkout-session` | 405 | POST-only, no secret needed (public action) |
| `/api/verse-request` | 405 | POST-only, no secret needed (public form) |
| `/api/stripe-webhook` | 405 | POST-only, gated by signature |

`POST /api/admin/orders` with a wrong password → **401** `Incorrect password.`
`PATCH /api/admin/orders` with no auth → **401**, and it is rejected *before* touching the DB, so it
cannot mark an order shipped.

### What is fine

- **The `/admin` HTML shell is served publicly (`200`) but leaks nothing.** The gate is
  client-side, so the page markup reaches anyone — but it contains no orders, no customer data and
  no secret. The grep over the live shell returned only the literal word "password" from the form
  label and `Order` from a heading. This is normal for a client-rendered page; the **API** is what
  actually protects the data, and it does.
- **`ADMIN_SECRET` is strong.** 64 characters, pure hex → **256 bits of entropy**. Not a
  weakness; do not "fix" this.
- **The secret never reaches the browser.** Only referenced in `src/pages/api/admin/orders.js`
  (server-side). No `NEXT_PUBLIC_` prefix.
- **Comparison is timing-safe** (`crypto.timingSafeEqual`) with a length check, so it does not leak
  the secret's length through timing.
- **`/admin` is `noindex, nofollow`** (verified in the live HTML) and is absent from
  `sitemap.xml`. `robots.txt` does not *disallow* it, which is the right call — a `Disallow` would
  prevent crawlers from ever seeing the `noindex`, and the page could still be indexed by URL.
- Cookie flags are correct: `HttpOnly`, `SameSite=Strict`, `Secure` in production, 8-hour expiry.

### Two genuine hardening gaps — minor, not critical

Neither is currently exploitable given the 256-bit secret, but both are worth knowing:

1. **No rate limiting on the admin login.** `POST /api/admin/orders` accepts unlimited password
   guesses. Against a 256-bit random hex secret this is not a practical attack, but it is the
   difference between "unattackable" and "unattackable *and* rate-limited". The pattern already
   exists in `src/pages/api/verse-request.js` (the in-memory `throttled()` helper) and could be
   reused. Note that any in-memory throttle is per-instance and only a speed bump.

2. **The session cookie stores the raw secret.** Signing in sets
   `vd_admin = <the ADMIN_SECRET itself>` rather than a derived session token:

   ```js
   `${ADMIN_COOKIE}=${encodeURIComponent(body.password)}`,
   ```

   Consequences: the long-lived master secret is now sitting in a browser cookie (8 hours), and
   rotating the secret invalidates nothing selectively — it changes the login *and* every existing
   cookie at once. A better shape is to sign a short-lived token (or store an HMAC of the secret)
   so the master value is never handed to the client. `HttpOnly` + `SameSite=Strict` + `Secure`
   already stop the realistic cookie-theft paths, which is why this is hardening rather than a hole.

Both are recorded here rather than fixed, because changing auth shape on a live site without being
asked is the kind of change that should be the owner's call.

### Audit conclusion

The admin surface is **in good shape**: every data-returning path is server-gated, the secret is
cryptographically strong, and the only public artifact is a static shell with no secrets in it.
The one outstanding *security* item across the whole audit remains the **§16 `dedications` column
leak**, which is a real, verified, live exposure and is the only one of the three that leaks data.
